按 《postcss-pxtorem 在 Vite5+Vue3 项目中如何配置》 与 《PostCSS Pxtorem 响应式设计及移动端适配》 两篇文章整理。核心只有一句话：编译期用 rootValue 把 px 换成 rem，运行期让 html 的 font-size 跟着屏幕走，两边基准必须都是设计稿的 1/10。

三个角色的分工

运行时 rem

1rem 对应的 px = html 的 font-size。html 字号一改，页面上所有 rem 尺寸等比跟着变，这就是整套方案能自适应的根。

html { font-size: 37.5px }
/* 此时 1rem = 37.5px */
.card { height: 1rem }   /* → 37.5px   */
.card { height: 2rem }   /* → 75px     */

编译期 postcss-pxtorem

构建时读 rootValue，把样式里的 px 除以它换成 rem。只在编译期跑，浏览器里没有它。

/* 源码 */  width: 100px;
/* rootValue: 75 */
/* 产物 */  width: 1.3333rem;

注意：行内样式 style="width:100px" 不会被转换，大写 PX 也会被跳过。

运行时 amfe-flexible

页面加载与 resize 时，把 html 的 font-size 设成 可视宽 ÷ 10。于是 rootValue 必须取设计稿宽 ÷ 10，两边才咬得上。

// 插件内部近似逻辑
docEl.style.fontSize =
  docEl.clientWidth / 10 + 'px'

第二篇的手写 setRem() 就是在做同一件事，只是多加了 clamp 上限。

一条完整的换算链（这是全文最重要的一屏）
① 设计稿750px 全屏宽→rootValue = 750 ÷ 10 = 75
② 编译期设计稿上 100px 的方块→100 ÷ 75 = 1.3333rem
③ 运行时 @750 屏html font-size = 750 ÷ 10 = 75px→1.3333 × 75 = 100px✓ 与设计稿 1:1
④ 运行时 @375 屏html font-size = 375 ÷ 10 = 37.5px→1.3333 × 37.5 = 50px✓ 等比缩一半
≡ 一般形式：实际渲染px = 设计稿px × (屏宽 ÷ 设计稿宽)。这也解释了为什么 rootValue 只能等于设计稿宽的 1/10 —— 它和 flexible 的“÷10”必须是同一个约定。
此刻，1rem 到底有多宽？

方案 A：flexible（屏宽 ÷ 10）

为什么两边必须对齐

        
插件负责“分子”，运行时负责“分母”。一边改了另一边没改，全站尺寸就会按固定倍数跑偏，而且每种元素偏得一样多，很难第一眼看出来。

PC 大屏（1920 稿）为什么不建议照搬

    

      
移动端可以无脑 屏宽÷10，因为手机屏宽区间窄。PC 从 1280 到 2560 差 2 倍，不加钳制的话 1rem 能从 128 涨到 256。第二篇给的 Math.min(scale, 2) 就是钳制，但只钳上限仍然会在小屏挤爆。

      

        

          
屏宽scale = 屏宽÷19201rem（base 192，clamp .667~1.5）设计稿 200px 元素实渲染若误用 rootValue:16

          
        

      

      

        !
        PC 端更稳的做法：布局尺寸用 px / clamp() / grid，字号用 clamp()，只把确实需要随屏缩放的模块用 rem。全量 rem 化在 PC 上收益低、心智负担高。

8 个真实会踩的坑

    

      

        
致命 rootValue 与运行时基准不一致

        
第二篇示例同时出现 rootValue: 16 和 html.fontSize = width / 75，两边差 4.7 倍，全站元素集体放大。

        
rootValue 必须 = 设计稿宽 ÷ 10，与 flexible 的 ÷10 同一个约定。

      

      

        
致命 Vite 配置里写 require()

        
vite.config.js 默认按 ESM 解析，require is not defined。

        
import postCssPxToRem from 'postcss-pxtorem'

      

      

        
高频 1px 边框被转成 rem

        
设计稿上的 1px 描边在大屏被放大成 2~3px，小屏又变成小数像素发虚。

        
propList: ['*', '!border*', '!font-size*']

      

      

        
高频 第三方组件库尺寸对不上

        
vant 设计稿 375、项目 750，共用一个 rootValue 必有一方错位。

        
rootValue ({ file }) { return /vant/.test(file) ? 37.5 : 75 }

      

      

        
易漏 行内样式 / JS 算出来的 px

        
el.style.width = '100px'、canvas、图表库的 fontSize 都不经过 PostCSS。

        
改成 100/rootValue + 'rem'，或统一走 CSS 变量

      

      

        
易漏 exclude: /node_modules/ 一刀切

        
把组件库整体排除后，组件内部该适配的尺寸也没了，页面出现“半适配”的割裂感。

        
exclude: /node_modules[\/](?!element-plus)/

      

      

        
注意 媒体查询里的 px 原样保留

        
默认 mediaQuery: false，断点仍是 px，而内部尺寸是 rem，两套单位混用容易算错。

        
断点统一用 px 就不要再在断点里写 rem 换算逻辑

      

      

        
架构 超宽屏不设上限

        
flexible 只做“屏宽 ÷ 10”，1440 屏上 1rem = 144px，PC 端会变成巨型页面。

        
scale = clamp(屏宽/设计稿, .667, 1.5) 后再乘 base

      

    


    
上手清单

    

      
    
        
  • 先定设计稿宽度，写进团队规范；改动设计稿等于改动 rootValue，全站一起动。
    • 
        
  • 装依赖：pnpm add postcss-pxtorem amfe-flexible -D（flexible 是运行时依赖，严格说不该 -D，但要随包上线）。
    • 
        
  • 配插件：rootValue = 设计稿 ÷ 10，propList 排除 border*、font-size*。
    • 
        
  • 接运行时：移动端引 amfe-flexible；PC 写带 clamp 的 setRem() 并监听 resize。
    • 
        
  • 验收：375 / 750 两个宽度各截一张图，元素位置比例应完全一致；再在大屏确认 1px 线没有变粗。
    • 
        
  • 兜底：容器最大宽度、栅格断点继续用 px；行内样式里的 px 手工处理。
